Root Cause: The root cause is an unbounded in-memory target registry in the DiscoveryScheduler that grows without any cap or eviction policy, inserting 5,000 entries every 5 seconds as observed in application logs (95,000 → 115,000 targets in 25 seconds). This continuous allocation exhausts the 512 MiB container memory limit, evidenced by Prometheus metrics showing 478/512 MiB (93.4%) at alert time and a confirmed java.lang.OutOfMemoryError in JFR exception data. When the heap is exhausted, the JVM triggers Serial GC (DefNew) due to 'Allocation Failure', but GC cannot reclaim enough memory since most objects are long-lived registry entries held in Tenured Generation, resulting in a 3.29-second stop-the-world pause. The container subsequently crashes, triggering the BackOff warning event observed at 08:51:11 UTC, and the cycle repeats on restart because the registry growth resumes immediately. No OOMKilled event is explicitly present in the provided Kubernetes events (only BackOff is recorded), but the combination of OutOfMemoryError, 93.4% memory saturation, and BackOff strongly indicates the container is being OOM-killed between event capture windows.

Solutions:
  1. Implement a bounded registry with a maximum size cap and eviction policy (e.g., LRU or TTL-based eviction) in the DiscoveryScheduler component to prevent unbounded memory growth (Probability: HIGH)
  2. Increase container memory limit to at least 948 MiB as recommended by Kruize, and set memory request to 948 MiB to guarantee resource allocation (Probability: MEDIUM)
  3. Replace the Serial GC (DefNew) collector with G1GC and tune heap settings to reduce stop-the-world pauses and improve memory reclamation efficiency (Probability: MEDIUM)
